# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This started as a freshly scaffolded Angular application (`ng new`, Angular CLI 21.2.24) with SSR enabled. `src/app/app.routes.ts` still has no routes defined, but the root `App` component now calls the backend (see below) as a working example of the frontend/backend connection. Architecture notes below describe the scaffold's structure so future work can build on it consistently; update this file as real features are added.

## Connection to the backend

This app is paired with a separate Express API at the repository root (`../app.js`, `../routes/api.js`) — see the root `CLAUDE.md` for the full picture. On this side:

- `provideHttpClient(withFetch())` and `provideZonelessChangeDetection()` are registered in `src/app/app.config.ts` — this app has no zone.js dependency, so it relies entirely on Angular signals for change detection; the explicit provider is required for that to be reliable rather than implicit.
- `src/app/services/api.ts` (`Api` service) wraps calls to the backend, e.g. `getHealth()` → `GET /api/health`.
- `proxy.conf.json` (repo root of `frontend/`) proxies `/api/*` to `http://localhost:3000` during `ng serve` — wired up via `serve.options.proxyConfig` in `angular.json`. This means components/services should call relative paths like `/api/health`, not `http://localhost:3000/api/health`.
- Run the root Express app (`npm start` from the repository root) alongside `ng serve` here to exercise the connection locally.
- The "Login" button in `app.html` sits in a plain `<form class="login-form">` alongside `jobupEmail`/`jobupPassword` string signals (both default `''`) driven by an Email (`type="email"`) and a Password (`type="password"`) input, both marked `required` — these are native HTML5 "built-in validators": the browser withholds the form's `submit` event (and shows its own inline validation message) for an empty field or a malformed email address, before any component code runs. The form also has its own "Use www.jobs.ch" checkbox next to the button (`loginUseJobsCh` signal, `onLoginUseJobsChChange` — independent of the CV Analysis job filters' own copy of this toggle below, see the root `CLAUDE.md`'s "www.jobs.ch support" section). The form's `(submit)` (not `(ngSubmit)` — this app has no `FormsModule` import, consistent with the rest of the codebase's plain-signal, no-Angular-Forms style) calls `onLoginSubmit($event)`, which `event.preventDefault()`s then calls `onLoginClick()`, which calls `Api.login({ email: jobupEmail(), password: jobupPassword(), useJobsCh: loginUseJobsCh() })` → `POST /api/login` with `{ email, password, useJobsCh }`, which runs a real jobup.ch (or jobs.ch) login automation on the backend using exactly those typed credentials and returns `{ success, message }`. `message` is `"Login succeeded !"` on success; on failure it's a specific, expected reason when the backend detected one (currently `"Invalid login credentials"` or `"Invalid email format"` — see the root `CLAUDE.md`'s `LoginValidationError` gotchas), else the generic `"Login failed !"` — same "specific reason when known, else generic" pattern as the CV Analysis flow's `errorMessage` below, just folded into `message` itself here rather than kept as a separate field, since the backend already knows the full display string either way. On success, the backend persists those same credentials back to the repo-root `.env` file, under whichever variable pair matches `useJobsCh` (`JOBSCH_EMAIL`/`JOBSCH_PASSWORD` or `JOBUP_EMAIL`/`JOBUP_PASSWORD`), so a later CV Analysis run for that same site (a separate, later-spawned backend process) picks them up automatically, no server restart needed; on failure, `.env` is left untouched. See the root `CLAUDE.md`'s "jobup.ch login automation" and "www.jobs.ch support" sections for how that works, how the persistence is implemented, and its limitations (including a confirmed dotenv quoting gotcha worth reading before touching `updateEnvFile()` again).
- The "CV Analysis" button in `app.html` calls `Api.cvMatch({ startJobIndex, endJobIndex, useBasicSearch, searchTerm, locations, saveJob, easyApply, ignoreYellowMeter, useJobsCh })` → `POST /api/cv-match`, which runs the jobup.ch job-search + AI CV-match automation on the backend for every job index in the `startJobIndex`..`endJobIndex` range (see the root `CLAUDE.md`'s "jobup.ch CV-match automation" section for the backend split behind this — one login+search, then one parallel worker per job index) and returns `{ success, errorMessage, totalJobsCount, resultsUrl, results }`. `success`/`errorMessage` are *request-level* — the search itself, or the Start/End index validation, failed — not about any individual job; the frontend picks the displayed message from `errorMessage` as-is when non-null (a specific, expected failure — e.g. jobup.ch reporting 0 matching jobs, an invalid index range, or `startJobIndex` itself out of range), else the generic "Analysis failed !"; on `success: true` it's always "Analysis succeeded !", even if some individual job within `results` failed (that job's own failure is shown inline instead — see `cvMatchResults` below). `totalJobsCount`/`resultsUrl` are shown whenever non-null *regardless* of `success` — still useful context (e.g. confirming a 0-match search, or letting the user open the actual results page jobup.ch searched) even when the whole request failed before any job was analyzed.
- `cvMatchResults` (`CvMatchJobResult[]`, from `response.results`) replaces the single-job `cvMatchAnalysis`/`cvMatchMeter`/`cvMatchCriteria`/`cvMatchJobUrl`/`cvMatchApplicationUrl` signals this used to be — one entry per job index actually analyzed (`{ jobIndex, success, analysis, meter, criteria, jobUrl, errorMessage, applicationUrl }` each), rendered in `app.html` via `@for (result of cvMatchResults(); track result.jobIndex)`, each in its own `.cv-match-job-result` block: a "Job {{ result.jobIndex }}" heading, `result.jobUrl`/`result.applicationUrl` links when present (the latter only ever non-null when `prepareJobApplicationDraft()` on the backend actually opened a draft application page — same conditions as before, just per-job now), then either `result.errorMessage` (a specific per-job failure, e.g. that job's own index landing out of range on its target page) if `!result.success`, or the parsed analysis box if it is. `segmentsFor(result)` in `app.ts` calls the same `parseAnalysis()` this used to feed from a single cached `computed()` — now a plain per-result method call in the template instead, since there can be several independent analyses shown at once. Each result's analysis box expands/collapses independently via `isAnalysisExpanded(jobIndex)`/`onToggleAnalysis(jobIndex)`, backed by a `collapsedJobIndexes` `Set` (tracking which are collapsed, not which are expanded, so a freshly-arrived result defaults to expanded without needing to be added to anything).
- `startJobIndex`/`endJobIndex` are 1-based signals (both default `1`) driven by the "Start job index :"/"End job index :" number inputs next to the CV Analysis button (`onStartJobIndexInput`/`onEndJobIndexInput` in `app.ts`) — together they select the *range* of jobs to analyze in parallel, each counted across all of the automation's search-result pages the same way the old single `jobIndex` was. The two are fully independent signals with no auto-sync; leaving `endJobIndex` at its own default (`1`) alongside `startJobIndex`'s default (`1`) reproduces the old single-job behavior with no extra action needed. See the root `CLAUDE.md`'s "jobup.ch CV-match automation" section for the exact validation rules and error messages (`'The Start and End job indexes must be a strictly positive integer'`, `'The End job index must not be lower than the Start job index'`, `'Start job index must not be greater than the number of jobs'` — the last of which is a hard, request-level failure only for `startJobIndex`; the same problem on any *other* index in the range is silently omitted from `results` instead).
- `searchTerm` and `locationInput` are string signals (both default `''`) driven by the "Search term :" and "Location :" text inputs next to the job index inputs (`onSearchTermInput`/`onLocationInput` in `app.ts`, both `maxlength="255"`, sized narrow so the whole `.cv-match-section` row still fits on one line). On submit, `onCvMatchClick()` trims `searchTerm`, and splits `locationInput` on commas, trims each part, and drops empty ones, before sending `searchTerm: string` and `locations: string[]` to the backend. `routes/api.js` trims/truncates (255 chars) and re-filters these again server-side, then forwards them to `scripts/jobup-search.js` (the one-time search step — not `jobup-cv-match.js`, which no longer runs any search of its own) as extra CLI args; the script falls back to its own `RECOVERY_SEARCH_TERM`/`LOCATION_SLUG` constants for whichever comes out empty, and — since "Rechercher avec mon profil" generates its own profile-derived term server-side — ignores `searchTerm` (and its fallback) entirely on any path where that CTA is actually used. Each location becomes its own repeated `location=` query param (not one comma-joined value) wherever the script applies a location filter. See the root `CLAUDE.md`'s "jobup.ch CV-match automation" section for the details and the known CTA-path location-filtering limitation this doesn't change.
- `useJobsCh`, `useBasicSearch`, `saveJob`, `easyApply`, and `ignoreYellowMeter` are boolean signals (all default `false`) driven by five checkboxes inside the "Job filters" dropdown next to the job index inputs (`jobFiltersExpanded` signal + `onToggleJobFilters()` in `app.ts` control the dropdown's open/closed state; `onDocumentClick()`, a `@HostListener('document:click')`, closes it on any click outside `.job-filters-dropdown` — deliberately independent of `cvMatchPending()`/the toggle button's `[disabled]` state, so a panel left open when a run starts can still be dismissed by clicking away even though the button itself won't respond to clicks while disabled). `useJobsCh` (`onUseJobsChChange`), the topmost checkbox: unchecked (default), the backend drives `www.jobup.ch` as usual; checked, it drives `www.jobs.ch` instead for the whole request (its own listings-page path, `/fr/offres-emplois/`, replacing jobup.ch's `/fr/emplois/`) — see the root `CLAUDE.md`'s "www.jobs.ch support" subsection, including why this is entirely unverified against jobs.ch's real markup. `useBasicSearch` (`onUseBasicSearchChange`): unchecked (default), the backend tries the profile-based "Rechercher avec mon profil" CTA first and only falls back to the basic-search entry point if it's unavailable; checked, it skips the CTA and goes straight to the basic-search entry point — mainly useful for exercising/testing that path directly without depending on jobup.ch account state. `saveJob`/`easyApply` (`onSaveJobChange`/`onEasyApplyChange`) gate the backend's "Sauvegarder"/"Candidature simplifiée" draft-preparation steps respectively, run independently *per job* now — see the root `CLAUDE.md`'s "jobup.ch automated application drafting" section; both are ignored server-side for any job whose own analysis has no meter at all. `ignoreYellowMeter` (`onIgnoreYellowMeterChange`): when checked, a yellow meter is treated as not-good-enough for `saveJob`/`easyApply` (only green then qualifies); unchecked (default), green and yellow are treated the same. Its checkbox is `[disabled]` (in addition to the usual `cvMatchPending()`) whenever both `saveJob` and `easyApply` are unchecked, since it has no effect on anything in that state — re-enabled the moment either one is checked. `onSaveJobChange`/`onEasyApplyChange` also call `resetIgnoreYellowMeterIfMoot()` after updating their own signal, which unchecks `ignoreYellowMeter` too (not just disables it) once both `saveJob` and `easyApply` are false, rather than leaving a checked-but-disabled, now-meaningless checkbox behind.
- `cdiOnly`/`cddOnly` ("CDI Only"/"CDD Only" checkboxes, right below "Use basic search" in the "Job filters" dropdown; `onCdiOnlyChange`/`onCddOnlyChange`, both default `false`) are sent with `POST /api/cv-match`; either one checked makes the backend apply jobup.ch's "Type de contrat" filter ("Durée indéterminée"/"Temporaire") to the search, neither checked leaves it unfiltered — see the root `CLAUDE.md`'s contract-type filter note.
- `backendStatus` (the "Backend status: …" badge) is set by the initial `getHealth()` check on load, and independently by the Login/CV Analysis calls' own `subscribe()` callbacks in `onLoginClick()`/`onCvMatchClick()` — both `next:` callbacks set `'connected'` unconditionally, both `error:` callbacks set `'unreachable'` unconditionally. This reflects HTTP-level reachability specifically, not automation success: any well-formed HTTP response — a real success, a specific known failure reason (e.g. `"Invalid login credentials"`, `"Invalid email format"`, `"0 job found, search term : ..."`, `"Job index must be a positive integer"`), or even the generic `"Login failed !"`/`"Analysis failed !"` (which can mean the backend hit a genuinely unexpected internal error, not that it's unreachable) — proves the Express server itself responded, so it always sets `'connected'`. Only a true network-level failure (the `error:` callback — connection refused, timeout, etc., with no HTTP response at all) means `'unreachable'`.
  - **Earlier design, reverted after a confirmed-live bug**: a previous version tracked `lastLoginSuccess`/`lastCvMatchSuccess` separately and only flipped to `'unreachable'` once *both* actions had been tried and *both* generically failed (reasoning: a single failed action alone shouldn't imply the backend is down). This broke in practice — stopping the backend server and clicking Login (without ever having tried CV Analysis) correctly triggered the `error:` callback and showed `"Login failed !"`, but `lastCvMatchSuccess` was still `null` (never tried, not `false`), so the "both failed" condition never matched and the badge stayed stuck on its previous value instead of flipping to `'unreachable'`. Confirmed live via a screenshot showing exactly that combination (a displayed `"Login failed !"` with the badge still *not* reading `'unreachable'`) before the fix, and the corrected badge immediately after. The "both must fail" heuristic was also redundant by the time this bug surfaced: it existed to avoid a false "unreachable" reading from one specific-reason failure, but that concern was already independently solved (see the root `CLAUDE.md`'s "jobup.ch login automation" gotchas) by the `next:`/`error:` split itself — a specific reason only ever arrives via `next:`, which already means `'connected'`.
- The square red "Stop analysis" icon button (`.stop-button` in `app.html`, next to "CV Analysis") is `[disabled]="!cvMatchPending()"` — the exact inverse of the "CV Analysis" button's own `[disabled]`, so exactly one of the two is ever clickable. Its `title`/`aria-label` (both set to "Stop analysis") give it an accessible name and a native tooltip, since its only visible content is the red square SVG. `onStopClick()` in `app.ts`: (1) unsubscribes from `cvMatchSubscription`, the `Subscription` `onCvMatchClick()` stored when it called `Api.cvMatch()` — this app uses `provideHttpClient(withFetch())`, so unsubscribing cancels the underlying fetch client-side, which matters because that `POST /api/cv-match` request stays open for the *whole* analysis (see the root `CLAUDE.md`'s "Stopping an in-progress analysis" section) and would otherwise eventually resolve and overwrite the reset this same click is about to do; (2) fires `Api.stopCvMatch()` → `POST /api/cv-match/stop` to actually kill the backend's still-running child process, fire-and-forget (the UI doesn't wait on its response); (3) calls `resetCvMatchState(false)` — the same state-clearing helper `onCvMatchClick()` calls with `true` at the start of a run, putting `cvMatchResult`/`cvMatchResults`/`cvMatchTotalJobs`/`cvMatchResultsUrl` back to `null`/`[]`, clearing `collapsedJobIndexes`, and setting `cvMatchPending` to `false`, i.e. exactly the pre-analysis state, rather than showing any "stopped"/failure message. On the backend, stopping now kills *every* process currently running for the request (the search, and/or whichever worker batch is in flight) — see the root `CLAUDE.md`'s "Stopping an in-progress analysis" section for how that changed once one request could have several child processes alive at once.

**Important**: `src/app/app.routes.server.ts` sets `RenderMode.Prerender` for all routes, so `ng build` renders the app once at *build time*, with no backend available. Any HTTP call made unconditionally in a component constructor (like the original health check) breaks that build. Guard such calls with `afterNextRender(() => { ... })` (see `app.ts`) so they only run in the browser, after hydration — never call `HttpClient` directly in a constructor on a prerendered route.

## Commands

Run all commands from the `frontend/` directory.

- `npm start` / `ng serve` — start the dev server at `http://localhost:4200/` with live reload.
- `ng build` — production build, output to `dist/`.
- `ng build --configuration development` — dev build (no optimization, source maps on).
- `npm test` / `ng test` — run unit tests via Vitest.
- `ng generate component <name>` — scaffold a new component (also `ng generate directive|pipe|service`, etc.); run `ng generate --help` for the full list.
- `node dist/frontend/server/server.mjs` — run the built SSR server (after `ng build`).

There is no e2e test runner configured, and no linter (e.g. ESLint) is set up yet.

## Architecture

- **Stack**: Angular 21 (standalone components, no NgModules), TypeScript 5.9 in strict mode, RxJS, Vitest for unit tests.
- **SSR**: The app is configured for server-side rendering via `@angular/ssr`.
  - `src/main.ts` — browser entry point.
  - `src/main.server.ts` — server entry point.
  - `src/server.ts` — Express server used to serve the SSR app.
  - `src/app/app.config.ts` — client-side app config (providers).
  - `src/app/app.config.server.ts` — server-side app config, merged with the client config for SSR.
  - `src/app/app.routes.server.ts` — server-only route rendering configuration (e.g. prerendering mode per route), separate from `src/app/app.routes.ts`.
  - The build's `outputMode` is `server` (see `angular.json`), meaning `ng build` produces both browser and server bundles under `dist/frontend/`.
- **Routing**: Client routes live in `src/app/app.routes.ts` (currently empty). Server-specific rendering behavior per route goes in `src/app/app.routes.server.ts`.
- **Components**: Standalone Angular components — no `@NgModule` declarations. Follow the existing `App` component's pattern (`app.ts` + `app.html` + `app.css`, using `imports: [...]` on the `@Component` decorator).
- **Testing**: Unit tests run through Angular's built-in Vitest builder (`@angular/build:unit-test`), not a standalone Vitest config. Test files are colocated with source as `*.spec.ts` (see `src/app/app.spec.ts`).
