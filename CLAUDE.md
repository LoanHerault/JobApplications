# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This is a single repository holding an Express backend and an Angular frontend as a subdirectory. There is no real business logic in the Express scaffold itself yet — update this file as the project takes shape.

1. **Root app** (`app.js`, `bin/`, `routes/`, `views/`, `public/`) — a stock Express 4 app generated by `express-generator`, using Jade templates. `routes/index.js` and `routes/users.js` are still the generator's defaults ("respond with a resource", etc.) and haven't been customized. `routes/api.js` is a real JSON API — it connects this app to the Angular frontend and drives the jobup.ch login and CV-match automations (see below).
2. **`frontend/`** — an Angular 21 SSR application, tracked as a plain subdirectory of this repo (not a nested git repo). See `frontend/CLAUDE.md` for its commands and architecture.
3. **`scripts/jobup-login.js`** — a standalone Playwright script, spawned as a child process by `routes/api.js`, that logs into jobup.ch (see below). Exports `dismissCookieConsent`/`performLogin`/`loginToJobup` so `scripts/jobup-search.js`/`scripts/jobup-cv-match.js` can reuse the login flow on their own page/browser instead of duplicating it; only runs as a CLI (reading env vars, printing JSON to stdout) when invoked directly.
4. **`scripts/jobup-search.js`** — a standalone Playwright script, spawned as a child process by `routes/api.js` exactly **once** per `POST /api/cv-match` request, that logs into jobup.ch (reusing `scripts/jobup-login.js`) and runs the job search, then saves the authenticated session to a temp Playwright `storageState` file for `scripts/jobup-cv-match.js`'s workers to load (see below).
5. **`scripts/jobup-cv-match.js`** — a standalone Playwright script, spawned as a child process by `routes/api.js` once **per requested job index**, in parallel, that loads the session `scripts/jobup-search.js` saved (no login of its own), picks the given job on the already-known results page, opens its AI CV-match analysis, and posts the analysis text back to the backend (see below).
6. **`scripts/jobup-shared.js`** — small helpers (`JOBS_PER_PAGE`, `dedupeByHref()`, `waitForJobResults()`, `EmptyResultsError`) shared between `scripts/jobup-search.js` and `scripts/jobup-cv-match.js`, split out so the two don't drift out of sync on things like the page-size constant. Not spawned as its own process — `require()`'d by (and, when bundled, inlined into) each of those two.
7. **`tests/`** — root-level Playwright e2e suite. Includes a spec that drives the same jobup.ch login *page* (navigation only, no credentials) for e2e coverage — separate from the `scripts/jobup-login.js`/`scripts/jobup-search.js`/`scripts/jobup-cv-match.js` automations used by the live features.
8. **`build.js`** — bundles and minifies the root Express app (via `npm run build`) into a deployable `dist/` folder. See "Backend build/deployment" below.

## Backend ↔ frontend connection

The Express app now serves a small JSON API, and the Angular app calls it:

- `routes/api.js` mounts `GET /api/health` (returns `{ status, service, timestamp }`).
- `app.js` mounts that router at `/api` and applies CORS scoped to that path, allowing `http://localhost:4200` (the Angular dev server) to call it directly.
- `frontend/proxy.conf.json` proxies `/api/*` requests from the Angular dev server to `http://localhost:3000`, wired up via `proxyConfig` in `frontend/angular.json`'s `serve` target — so in practice CORS is a fallback and the proxy is the normal dev path.
- `frontend/src/app/services/api.ts` (`Api` service) calls `/api/health` via `HttpClient`; `frontend/src/app/app.ts` calls it on init and renders the result (`backendStatus` signal) in `app.html`.

**To see it working**: run `npm start` at the root (Express on port 3000) and `npm start` in `frontend/` (Angular dev server on port 4200) at the same time, then open `http://localhost:4200` — it should show "Backend status: connected".

This wiring only covers local development (the dev-server proxy and CORS for `localhost:4200`). There's still no production integration — nothing yet decides whether Express serves the built Angular app, proxies to it, or the two are deployed as fully separate services.

## jobup.ch login automation

The frontend has Email/Password inputs, a "Login" button, and a "Use www.jobs.ch" checkbox (`frontend/src/app/app.html`/`app.ts`, inside a plain `<form>`) that triggers a real login attempt against jobup.ch (or jobs.ch, per the checkbox) through the backend, using whatever credentials were just typed:

1. Form submit (native `(submit)`, not `(ngSubmit)` — this app doesn't use Angular's `FormsModule` anywhere; see `frontend/CLAUDE.md`) → `onLoginSubmit()` calls `event.preventDefault()` then `onLoginClick()` → `Api.login({ email, password, useJobsCh })` (`frontend/src/app/services/api.ts`) → `POST /api/login` with `{ email, password, useJobsCh }`. The Email input's `type="email"` and both inputs' `required` attributes are native HTML5 "built-in validators" — the browser blocks the form's `submit` event entirely (with its own validation UI) for an empty field or a malformed email, before any of this ever runs; no custom JS validation exists or is needed.
2. `routes/api.js`'s `/login` handler trims `email`, takes `password` as-is (never trimmed — a password's leading/trailing characters are meaningful), and — if either is empty — short-circuits to `{ success: false, message: 'Login failed !' }` without spawning anything (defense in depth; the frontend's native validators should already prevent this). Otherwise it spawns `scripts/jobup-login.js` as a **child process** (`child_process.execFile`), passing `useJobsCh` as a CLI arg and `email`/`password` through the spawned process's *environment*, under whichever variable name matches the site (`JOBSCH_EMAIL`/`JOBSCH_PASSWORD` or `JOBUP_EMAIL`/`JOBUP_PASSWORD` — see the "www.jobs.ch support" subsection below for the full two-checkbox/two-credential-pair picture) — overriding whatever this server process's own value for that pair currently is, so the attempt always uses exactly what was just typed, not a stale value — and awaits it.
3. `scripts/jobup-login.js` launches a headless Chromium browser via Playwright, drives the selected site's actual login flow using that same site-matching credential pair from the environment, and prints one line of JSON to stdout: `{"success": true|false}`.
4. The Express handler parses that JSON and responds with `{ success, message: "Login succeeded !" }` or `{ success, message: "Login failed !" }`, which the frontend displays next to the button.

**Setup**: copy `.env.example` to `.env` at the repo root and fill in real credentials for whichever site(s) you use (`JOBUP_EMAIL`/`JOBUP_PASSWORD` for jobup.ch, `JOBSCH_EMAIL`/`JOBSCH_PASSWORD` for jobs.ch — either or both) — this remains the *initial* setup step, before the app has ever been used, or as a manual fallback. `app.js` loads it via `dotenv` at startup. `.env` is gitignored — never commit real credentials. `playwright` is a direct production dependency (not just a transitive devDependency of `@playwright/test`) specifically so this script keeps working in a production install.

**Persisting a successful login back to `.env` (so a later CV-match run picks it up with no server restart)**: on a successful login (CLI invocation only, i.e. the real flow above — not when `scripts/jobup-search.js` reuses `dismissCookieConsent`/`performLogin` for its own login step, which never touches `.env`), `scripts/jobup-login.js`'s bottom CLI block calls its own `updateEnvFile(path.join(process.cwd(), '.env'), { [emailVar]: email, [passwordVar]: password })` — `emailVar`/`passwordVar` being whichever site-matching pair (`JOBSCH_EMAIL`/`JOBSCH_PASSWORD` or `JOBUP_EMAIL`/`JOBUP_PASSWORD`) that same login attempt's own `useJobsCh` selected (see "www.jobs.ch support" below) — rewriting just those two lines in place (preserving every other line — comments, blank lines, unrelated vars, and the *other* site's own pair — and their original order) and leaving the file completely untouched on a failed login (the call only happens inside the `if (success)` branch). A failure to write the file (e.g. permissions) is caught and logged to stderr separately — it does **not** turn an otherwise-successful login into a reported failure.
- `routes/api.js`'s own `process.env` values for either pair were only ever set *once*, by `dotenv.config()` in `app.js` at server startup — mutating them at runtime, or relying on a spawned child's default env inheritance from this long-running process, would never reflect a login that happened *after* startup. Instead, `readCurrentJobupCredentials(useJobsCh)` in `routes/api.js` re-reads and re-parses the `.env` file fresh (via `dotenv.parse(fs.readFileSync(...))`) on **every** `POST /cv-match` request, and passes the matching pair into that request's own spawned `scripts/jobup-search.js` child via the same `env:` override mechanism as `/login` above — so a login submitted after the server started is picked up by the very next analysis for that same site, with no restart. Falls back to this process's own `process.env` (the original startup value) if the file is missing/unreadable.
- **`updateEnvFile()`'s value-quoting had a real, confirmed bug worth knowing about if this needs touching again**: an initial version wrapped values in double quotes and escaped an embedded `\`/`"` as `\\`/`\"`, on the assumption dotenv would unescape those back on read (matching how many other config-file formats work). It does not — **confirmed by reading the installed dotenv version's own parser source**: a double-quoted value's matching outer quote pair is stripped, and a literal `\n`/`\r` two-character sequence is unescaped into a real newline/CR — and that is the *only* unescaping it performs; a backslash before a quote or another backslash is recognized *only* for finding where the quoted value actually ends (so the regex doesn't stop at an internal, intentionally-escaped quote), but is never stripped back out of the resulting value afterward. Writing `\"` for an embedded `"` therefore left a literal, wrong backslash in the value once read back — corrupting any password containing a `"`. **Fixed**: `formatEnvValue()` no longer escapes `"`/`\` at all (confirmed via a round-trip test covering `#`, spaces, backslashes, and an embedded `"` — the last of which happens to still round-trip correctly through this dotenv version's regex, via a fallback path where the unescaped internal `"` causes its primary double-quote-matching alternative to fail and fall through to the unquoted-value alternative instead, which is then quote-stripped generically — but this is treated as unreliable/undocumented behavior, not relied upon), and only escapes a literal embedded newline/CR into the `\n`/`\r` two-character sequence dotenv *does* correctly reverse. A value containing a literal `"` now logs a stderr warning (rather than silently risking corruption) since lossless round-tripping of that specific character isn't guaranteed by this dotenv version at all, quoting strategy aside.

**How the flow was reverse-engineered** (useful if jobup.ch changes and selectors need updating): jobup.ch has two different cookie-consent variants that appear inconsistently between sessions — a plain `alert` with an exact-text "ok" button, and a fuller GDPR `dialog` with a "Accepter tous les cookies" button; `scripts/jobup-login.js` checks for both. The "Se connecter" control is a `<button>` (`id="user-nav-login-link"`), not a link — clicking it opens an Auth0-hosted universal-login flow at `auth.jobup.ch` with no stable URL to `goto()` directly. That flow is two-step: an email textbox ("Adresse e-mail") + a "Continuer" button (use `exact: true` — there are also "Continuer avec Google"/"Continuer avec Apple" buttons that substring-match "Continuer"), then a password textbox ("Mot de passe") + the same "Continuer" button. On failure the page shows the text "E-mail ou mot de passe incorrect" and stays on `auth.jobup.ch`; on success it redirects away from that host. The script races those two outcomes with a 20s timeout.

**Gotcha already hit once**: the cookie-consent overlay fades in over ~200ms, so checking it with `.isVisible({ timeout })` is unreliable — that method checks immediately rather than actually waiting for the element to appear, so it can return `false` before the dialog has mounted, silently skip both branches, and then the overlay blocks every subsequent click (including "Se connecter") until Playwright's default 30s action timeout is exhausted. Use `.waitFor({ state: 'visible', timeout })` instead (raced across both variants with `Promise.race`), which properly waits. Both `scripts/jobup-login.js` and `tests/jobup-login.spec.ts` use this pattern now — don't reintroduce `.isVisible()` for this check.

**Gotcha #2, confirmed live via a user-supplied server log and DOM snippet**: "E-mail ou mot de passe incorrect" (`<span id="error-element-password" class="ulp-input-error-message" data-error-code="wrong-email-credentials">`) can appear right after the **email** step — before the password textbox ever renders — not just after the password step, which is the only place the original version checked for it. When this happens, the original code went straight into `.fill()`-ing the password textbox, which doesn't exist yet, and waited out the full default 30s Playwright action-timeout before throwing an opaque `TimeoutError: locator.fill: Timeout 30000ms exceeded. ... waiting for getByRole('textbox', { name: /mot de passe/i })` — the real, known cause (wrong/unrecognized email) was completely lost in that generic timeout. **Fixed**: `performLogin()` now races the password field's own appearance against that same error text immediately after the email step too (mirroring the existing password-step race), and throws a new `InvalidCredentialsError` (see the shared `LoginValidationError` base class below) the moment that error text is detected at *either* step, instead of letting it silently time out. This is reported explicitly rather than as a raw error dump: the CLI's catch block logs a single `Invalid login credentials.` line (see the "logging" gotcha below for why this doesn't carry its own `[jobup-login]` prefix) and includes `errorMessage: 'Invalid login credentials'` in its stdout JSON; `routes/api.js`'s `/login` handler uses that as the `message` shown to the user instead of the generic `'Login failed !'`. Since `performLogin()` is shared with `scripts/jobup-cv-match.js` (see the "jobup.ch CV-match automation" section), its own login step there now also catches this the same way its other expected failures are — rather than letting the exception propagate uncaught into its generic catch-all.

**Gotcha #3, confirmed live via a user-supplied DOM snippet, same shape as #2**: Auth0's own client-side email-format validator can reject the typed email right after the email step too, via a *different* error element — `<div id="error-cs-email-invalid" class="ulp-error-info aria-error-check ulp-validator-error" data-ulp-validation-function="ulpEmailValidationFunction" ...>Saisissez une adresse e-mail valide (par exemple, user@domain.com).</div>` — which would have hit the exact same opaque-30s-timeout failure mode as #2 if left unhandled. This is a genuinely reachable case despite the frontend's own `type="email"` input validation (see `frontend/CLAUDE.md`): Auth0's validator is stricter than a browser's native email-format check, so a value that passes the browser's check can still be rejected here. **Fixed the same way, generalized**: `InvalidCredentialsError` and this new `InvalidEmailFormatError` (message `'Invalid email format'`) now both extend a shared `LoginValidationError` base class (all three exported from `scripts/jobup-login.js`), and `performLogin()`'s email-step race checks for *both* error texts alongside the password field's own appearance. Both call sites (the CLI block here, and `scripts/jobup-cv-match.js`'s login step) catch the shared `LoginValidationError` base class rather than each specific subclass — using `err.message` directly as the reported `errorMessage` — so a *future* subclass added the same way is automatically reported correctly without needing to touch either call site again.

**Logging gotcha**: an uncaught error from `performLogin()`/`loginToJobup()` used to be logged via a raw `console.error(err)`, which dumps Playwright's full multi-line error (call log, stack trace, and any extra own-properties like `{ log: [...], name: 'TimeoutError' }`) into the backend console as an opaque blob. The CLI's generic catch block now logs a single explicit line instead — `'login automation failed unexpectedly: ' + err.name + ': ' + err.message'` — dropping the raw stack trace and property dump while keeping the actually-useful part (Playwright embeds its own "Call log: - waiting for ..." detail directly in `.message`, so that part is preserved). This is a different code path from the `InvalidCredentialsError` case above, which has its own, even more specific one-line message.

**No `[jobup-login]`/`[jobup-cv-match]` prefix in either script's own `console.error()` calls** (confirmed live: they were showing up doubled, e.g. `[jobup-login] [jobup-login] Invalid login credentials.`) — `routes/api.js` already prepends that prefix exactly once, itself, whenever it forwards a spawned script's stderr to the backend console (`console.error('[jobup-login]', stderr.trim())` / `console.error('[jobup-cv-match]', stderr.trim())` — see both route handlers). Every `console.error(...)` call inside `scripts/jobup-login.js` and `scripts/jobup-cv-match.js` should stay prefix-free for this reason; add the bare message only, and let `routes/api.js` own the prefixing.

**Known limitation**: this drives Auth0's real, live login form, so any change to its markup, copy, or flow (or a CAPTCHA/rate-limit challenge triggered by too many automated attempts in a short window) can break the selectors or the success/failure heuristic above. Re-derive them the same way this was built: run the script directly (`JOBUP_EMAIL=... JOBUP_PASSWORD=... node scripts/jobup-login.js`) and inspect `page.locator('body').ariaSnapshot()` at each step rather than guessing.

## jobup.ch CV-match automation

`POST /api/cv-match` runs a job-search + AI CV-match flow for a *range* of job indexes (`startJobIndex`..`endJobIndex`, both 1-based and inclusive — see the frontend's "Start job index :"/"End job index :" inputs). Every selector below has been verified end-to-end against the live site (each was wrong at least once first — see "Selector gotchas" below for what jobup.ch's markup actually looks like and why the obvious guess didn't work) — except the multi-location `location=` query-param behavior noted where it's used below, and the two pieces explicitly flagged unverified in "The search/per-job split" right below, all of which hasn't been re-verified since this section was last touched.

### The search/per-job split

Analyzing a *range* of jobs in parallel, while only logging in and searching once, needs two separate scripts rather than the one this used to be — a single Playwright browser/process can't do "spawn N parallel workers that are all logged in" by itself. `routes/api.js` now:

1. Spawns `scripts/jobup-search.js` **once** per request — it does everything through reading `resultsUrl`/`totalJobsCount` (steps 1–2 below, relocated from the pre-split script unchanged), then calls Playwright's `context.storageState({ path })` to save the authenticated session's cookies/localStorage to a temp file (`os.tmpdir()/jobup-session-<uuid>.json`) and prints `{ success, errorMessage, totalJobsCount, resultsUrl, storageStatePath }`.
2. Validates `startJobIndex`/`endJobIndex` (see `routes/api.js`'s own `/cv-match` doc comment for the exact rules and error messages — `'The Start and End job indexes must be a strictly positive integer'`, `'The End job index must not be lower than the Start job index'`, and `'Start job index must not be greater than the number of jobs'`, checked two ways — see the confirmed-live bug/fix right below for why both exist). An out-of-range index *other* than `startJobIndex` (e.g. `endJobIndex` landing past the real total) is silently omitted from the results rather than failing the request.
3. Spawns `scripts/jobup-cv-match.js` **once per job index** in the (validated, clamped) range, in parallel batches of 5 (`runWorkersInBatches()`) — not fully unbounded, since jobup.ch has documented CAPTCHA/rate-limit sensitivity to bursts of automated activity (see the login section above); the user explicitly chose a capped batch size over firing every worker in the range at once. Each worker is given `resultsUrl`, `storageStatePath`, its own single `jobIndex`, and the save/apply filters — it launches its **own** browser, loads the saved session via `browser.newContext({ storageState: storageStatePath })` (no login UI interaction at all — see `dismissCookieConsent()`'s call right after as a cheap defensive no-op, not a real fallback login), navigates straight to `resultsUrl`, and does steps 3–6 below for that one job.
4. Deletes the temp `storageState` file once every worker has finished with it.

**Both pieces of this split are now confirmed live:**
- **Worker `storageState` authentication — confirmed live.** A real run with `startJobIndex=1`/`endJobIndex=3` (search entry via the subNavTab fallback, `totalJobsCount: 29`) spawned 3 parallel workers off the one saved `storageState` file; all 3 landed on the authenticated results page with no login-page/unauthenticated fallback, each independently rendered its own job-order dump, opened its target job, and posted a real analysis (`meter`/`criteria` correctly populated for jobs 1 and 3, `meter: null` correctly detected and save/apply correctly skipped for job 2's "Vos talents correspondent mieux à d'autres opportunités" rejection page) — no errors, no timeouts.
- **Pagination in a worker — confirmed live.** A follow-up run with `startJobIndex=18`/`endJobIndex=22` (crossing the `JOBS_PER_PAGE`=20 boundary, so some of those workers had `targetPage = 2`) succeeded — the URL-based `?page=N` navigation `runCvMatchJob()` tries unconditionally first worked without needing the click-based "next page" fallback, even for workers whose search may have originally gone through the direct-CTA path. No `ERR_TOO_MANY_REDIRECTS`, no wrong-page landings.

**Bug confirmed live, then fixed: an out-of-range `startJobIndex` whose `targetPage` exceeds the real number of pages can silently return a real, WRONG job instead of the expected out-of-range error.** `startJobIndex=50`/`endJobIndex=51` against `totalJobsCount: 29` (targetPage = ceil(50/20) = 3, but only 2 real pages existed for 29 jobs) returned a real job — "Un bon départ", a genuine analysis — instead of `'Start job index must not be greater than the number of jobs'`. Root cause: `routes/api.js` originally trusted the worker's own per-page job count as the *sole* authority for this check (deliberately, since `totalJobsCount` has a separate, already-documented under-counting bug on ≤20-result searches — see the search step below) — but jobup.ch doesn't throw or render an empty page for an out-of-range `?page=N` request; it silently serves *some other, valid* page instead, so the worker's "does this page have enough jobs" check passed against that wrong page and returned one of its real jobs, with no error at all. **Fixed**: `routes/api.js`'s `/cv-match` handler now also checks `startJobIndex > totalJobsCount` directly (when `totalJobsCount` is non-null) *before* ever spawning a worker for it, short-circuiting to the same out-of-range error — safe specifically because the only confirmed `totalJobsCount` inaccuracy is under-counting a *single-page* (≤`JOBS_PER_PAGE`) result set, which can't apply once `startJobIndex` needs pagination (`targetPage > 1`) at all. When `totalJobsCount` is `null` (parse failure), this check can't run, so the worker's own per-page result remains the fallback authority — unchanged from before, and not otherwise re-verified against jobup.ch's page-clamping behavior described above.

### www.jobs.ch support

Two independent "Use www.jobs.ch" checkboxes drive `www.jobs.ch` instead of `www.jobup.ch`, each scoped to its own flow — checking one has no effect on the other:

- The Login button's own copy (`app.html`, next to that button — `loginUseJobsCh` signal in `app.ts`, separate from the one below) sends `useJobsCh` through `POST /api/login` → `routes/api.js` → `scripts/jobup-login.js`'s `process.argv[2]`.
- The CV Analysis job filters' copy (in the "Job filters" dropdown, above "Use basic search" — see `frontend/CLAUDE.md`) sends `useJobsCh` through `POST /api/cv-match` → `routes/api.js`'s `runSearchScript()` → `scripts/jobup-search.js`'s own `process.argv[5]`, driving that request's search *and* every one of its per-job workers.

Only a few places are actually domain-specific — everything else in every script already builds its URLs by mutating the *current* page's own already-loaded URL (`new URL(page.url())`, `resultsUrl`), which naturally carries whichever domain was loaded:

- `scripts/jobup-login.js`'s `loginToJobup()` and `scripts/jobup-search.js`'s `BASE_URL`/`JOBS_PATH` (`'https://www.jobup.ch'` + `'/fr/emplois/'`, or `'https://www.jobs.ch'` + `'/fr/offres-emplois/'` — jobs.ch's own jobs-listing path, given by the user) — used for the initial navigation(s) that kick off the rest of each flow.
- `scripts/jobup-cv-match.js`'s `runCvMatchJob()` resolves a selected job's relative `href` against `new URL(resultsUrl).origin` rather than a hardcoded `'https://www.jobup.ch'` — since `resultsUrl` already carries whichever domain the search actually used, the worker needs no `useJobsCh` parameter of its own at all.
- `scripts/jobup-login.js`'s `performLogin()` also generalized its Auth0 success check from `!url.hostname.includes('auth.jobup.ch')` to `!url.hostname.startsWith('auth.')` — jobs.ch's own Auth0-hosted login page is confirmed (user-supplied URL) to live at `auth.jobs.ch/u/login`, a genuinely separate host from jobup.ch's `auth.jobup.ch`, so the generalized, prefix-based check is what makes this work for both without hardcoding either.

**Separate credential pairs, picked by the same checkbox that's driving each flow.** `.env` holds two independent pairs — `JOBUP_EMAIL`/`JOBUP_PASSWORD` (the original, default pair) and `JOBSCH_EMAIL`/`JOBSCH_PASSWORD` (see `.env.example`) — and every script/route below picks between them the same way, by the site its own `useJobsCh` selected, never mixing the two:
- `scripts/jobup-login.js`'s CLI block reads/writes `JOBSCH_EMAIL`/`JOBSCH_PASSWORD` when its `useJobsCh` arg is set, `JOBUP_EMAIL`/`JOBUP_PASSWORD` otherwise — including the post-success `updateEnvFile()` call, which now rewrites whichever pair was actually used, never the other one.
- `routes/api.js`'s `POST /login` mirrors this: it overrides the spawned child's env with the *matching* variable name (`JOBSCH_EMAIL`/`JOBSCH_PASSWORD` or `JOBUP_EMAIL`/`JOBUP_PASSWORD`) set to whatever was just typed in the form, so the script's own read (above) picks it up regardless of which pair — or neither, yet — currently exists in `.env`.
- `routes/api.js`'s `readCurrentJobupCredentials(useJobsCh)` (renamed from a jobup.ch-only name, used by `runSearchScript()`) re-reads `.env` fresh on every `POST /cv-match` request and returns the matching pair under its own key name, the same "fresh read, no restart needed" behavior the pre-jobs.ch version had for `JOBUP_EMAIL`/`JOBUP_PASSWORD` alone.
- `scripts/jobup-search.js`'s own CLI block mirrors `jobup-login.js`'s: reads `JOBSCH_EMAIL`/`JOBSCH_PASSWORD` when its own `useJobsCh` arg is set, `JOBUP_EMAIL`/`JOBUP_PASSWORD` otherwise.
- `scripts/jobup-cv-match.js` (the per-job worker) needs no credentials of its own at all — it never logs in, only loads the `storageState` `jobup-search.js` already saved.

**Confirmed live (first real end-to-end run, `useJobsCh` on both checkboxes): login, search, and job selection/analysis all worked against jobs.ch** — same selectors, same flow, no code changes needed beyond the domain-switching plumbing above. A `startJobIndex=1`/`endJobIndex=50` run against 44 real jobs.ch results (term "développeur fullstack", location "Genève") correctly logged in, found the results, and successfully read a full analysis (meter/criteria/list rendering all correct) for jobIndex 1.

**But the same run also surfaced a genuine, separate issue — not domain-specific markup, timing under concurrent load**: jobIndexes 2, 5, 8, 9, and 10 (split across two different 5-worker batches — not every worker in either batch, so not a batch-wide failure) all timed out with the exact same `TimeoutError: locator.waitFor: Timeout 60000ms exceeded` waiting for the analysis modal's "Fermer" button, inside `readAnalysisAndClose()`'s 60s wait for a *new* analysis to finish generating. ### The search step (`scripts/jobup-search.js`, run once)

`POST /api/cv-match`'s body takes `searchTerm` (string) and `locations` (string[]), from the frontend's "Search term :"/"Location :" text inputs (comma-separated, trimmed, and split into `locations` client-side — see `frontend/CLAUDE.md`). `routes/api.js` trims/truncates them (255 chars) again and forwards them as extra CLI args to `scripts/jobup-search.js`. Inside that script, `effectiveSearchTerm`/`effectiveLocations` fall back to the fixed `RECOVERY_SEARCH_TERM`/`[LOCATION_SLUG]` defaults whenever the caller-supplied value is empty — **except** `effectiveSearchTerm`, which is only ever read on the two codepaths below that already run *because* "Rechercher avec mon profil" wasn't available, so a custom or default search term is naturally ignored whenever that CTA is actually used (it generates its own profile-derived term server-side, with no term field for this script to influence). Each location in `effectiveLocations` is appended as its own repeated `location=` query param (`appendLocations()`), not one comma-joined value.

1. Logs into jobup.ch by reusing `dismissCookieConsent`/`performLogin` from `scripts/jobup-login.js` (same page/browser, not a second process), then navigates to `https://www.jobup.ch/fr/emplois/`.
2. Clicks "Rechercher avec mon profil" — or, if `useBasicSearch` is true (from `POST /api/cv-match`'s body, defaulting to false; the frontend's "Use basic search" checkbox next to the CV Analysis button), skips straight to the "Recherche d'emploi" sub-nav tab / basic-search entry point instead (mainly useful for exercising/testing that path directly without depending on account state). Either way, `/fr/emplois/` can independently render in "Intelligent search" mode (broader/semantic results, sparkle "Recherche" button) or "Basic search" mode (the classic filter UI, narrower/literal results), regardless of entry point — see the search-mode-detection gotcha below for how the script detects and handles both: `useBasicSearch` true goes straight to Basic search mode and `effectiveSearchTerm`; the natural sub-nav-tab fallback (CTA/role unavailable, `useBasicSearch` false) detours through Intelligent search mode looking for "Rechercher avec mon profil" there, and if that's not found either, navigates directly to the results URL with `term=<effectiveSearchTerm>` and `location=<...>` (one per `effectiveLocations` entry) set as query params — staying in Intelligent search mode rather than falling back to Basic search mode, since Intelligent mode returns substantially more results for the same term/location (confirmed live: ~195 vs. ~18). Otherwise (when a term field was actually filled through the UI), once page 1's results render (confirming the URL has synced with the real `term`), applies a location filter by navigating to that URL with `effectiveLocations` appended (see the location-filtering gotcha below for why this replaced clicking "Utiliser ma localisation", and why it only works on the basic-search path). Reads the total match count from the "... offres d'emploi" text near the top of the page as `totalJobsCount` (a supplementary value — logs and continues with `null` if it can't be found/parsed, doesn't fail the run) — **except** when that parsed number is `JOBS_PER_PAGE` (20) or less: confirmed live, that text can simply be wrong on a small result set (seen reporting `1` while 3 distinct job cards actually rendered on the page), so whenever every match is guaranteed to already fit on this one page (no pagination involved), the actual rendered `[data-cy="job-link"]`/`role="article"` cards are counted directly (deduped the same way `dedupeByHref()` already handles the promotional-widget-duplicate case elsewhere) and that count overrides the parsed text instead. Above `JOBS_PER_PAGE` this isn't attempted, since counting only this page's DOM elements can't tell you the true total across every page. If the term/location combination matches 0 jobs, jobup.ch renders a `[data-cy="empty-result"]` element instead of any job link — `waitForJobResults()` (now in `scripts/jobup-shared.js`, shared with the per-job worker below) races against that element (alongside the normal job-link wait) and, if it wins, throws an `EmptyResultsError` that `runSearch()` catches specifically and turns into an immediate `{ success: false, totalJobsCount: 0, errorMessage: '0 job found, search term : '<effectiveSearchTerm>', locations : '<effectiveLocations.join(', ')>'' }` — rather than the 20s Playwright `TimeoutError` this used to surface for what is actually a normal, expected outcome. `errorMessage` is `null` on every other return path; `routes/api.js` forwards it as-is (instead of the generic "Analysis failed !") whenever it's present.

### The per-job step (`scripts/jobup-cv-match.js`, run once per job index, in parallel)

3. Given `resultsUrl` and its own single `jobIndex` (no more search of its own — see "The search/per-job split" above), selects the `jobIndex`-th (1-based, across all result pages) job offer. First navigates to `resultsUrl` and waits for page 1's results to actually render; a non-positive-integer `jobIndex` is guarded against here too (defense in depth — `routes/api.js` already validates the whole range before spawning any worker) as `{ success: false, errorMessage: 'Job index must be a positive integer' }`. jobup.ch paginates at `JOBS_PER_PAGE` (20) per page: an index beyond the first page reaches the right page (`targetPage = Math.ceil(jobIndex / 20)`) by navigating directly to `?page=<targetPage>`, falling back to clicking a "next page" control repeatedly if that navigation throws (see "The search/per-job split" above for why both exist and which is unverified). Then selects position `((jobIndex - 1) % 20) + 1` *within* that page (not the simpler `jobIndex % 20`, which would give an invalid position 0 for exact multiples of 20); if that position exceeds the number of jobs actually found there, returns `{ success: false, errorMessage: 'Job index must not be greater than the number of jobs found on that page' }` (note: this is the count of job cards found *on that specific page*, which can differ from `totalJobsCount`'s overall search-match count — e.g. a small result set with a promotional/recommended card mixed in, as seen live). Reads the selected job's real detail-page URL (`https://www.jobup.ch/fr/emplois/detail/...`) from the link's `href` attribute *before* clicking it as `jobUrl` — jobup.ch renders the job detail in place rather than navigating there (it just adds a `?jobid=...` query param to the *listing* page's URL), so `page.url()` after the click would be the wrong thing to use here.
4. If that job was already analyzed in a previous run, jobup.ch shows a "Voir l'analyse" button (read the existing result) instead of "Voir mon match" (run a new analysis, then confirm with "Continuer") — the script detects and handles both.
5. Waits (up to 60s for a new analysis, 20s for an existing one) for the "Fermer" button on the analysis dialog to appear as the signal that the result is ready, reads the dialog's text as the analysis result, plus its structured `meter`/`criteria` (see below), `POST`s all three as `{ analysis, meter, criteria }` to `${BACKEND_URL}/api/cv-analysis` (`BACKEND_URL` defaults to `http://localhost:3000`), then clicks "Fermer".
6. Prints `{"jobIndex": number, "success": true|false, "analysis": string|null, "meter": object|null, "criteria": array, "jobUrl": string|null, "errorMessage": string|null, "applicationUrl": string|null}` to stdout — `totalJobsCount`/`resultsUrl` are no longer part of this per-job output (they're request-level now, reported once by `routes/api.js` from the search step, not duplicated per job); see `routes/api.js`'s own `/cv-match` doc comment for the full request/response shape.

`routes/api.js`'s `POST /cv-analysis` handler is the receiving end: it just validates and `console.log`s the analysis text (plus `meter`/`criteria` if present) — no persistence yet, revisit if this needs to be stored/displayed somewhere.

**Structured `meter`/`criteria` extraction** (`extractAnalysisStructure()` in `scripts/jobup-cv-match.js`): the analysis dialog's overall-match meter and each criterion's met/partial/not-met status are conveyed only by icon/fill *color*, not text, so they don't survive the plain `.innerText()` read step 5 also does. Unlike every other selector in this file, this one was **not** verified end-to-end live (no jobup.ch session was available in that environment) — it was derived from a one-off user-supplied DOM dump of a real analysis modal instead:
- Each criterion row has a `<span class="c_green.400 ... icon icon--iconSize_sm">` (met), `c_yellow.300` (partially met), or `c_gray.700` (not met) wrapping a decorative, textless SVG — classified by checking the class string for `c_green`/`c_yellow`/`c_gray`. That icon span has no text of its own, so its own parent element's `innerText` is exactly that row's title (plus explanation line, if the AI gave one) with no icon noise mixed in; `criteria` is that `{ text, status }` per row.
- The meter is one colored fill div, whose own class gives both the color (`bg_green...`/`bg_yellow...`) and width, either as a fraction token (`w_1/3`) or an arbitrary-value token (`w_[45%]`) — parsed into `{ color, percent }`. **Bug hit here** (confirmed live, from user-reported logs): the first version scoped the search by first `querySelector`-ing a "gray track" ancestor (class contains `bg_gray.200`), then looking for a `bg_`-classed child inside it — but the analysis modal can contain other `bg_gray.200`-classed elements for unrelated purposes, and `querySelector()` silently grabbed the wrong one, always yielding a false-negative `meter: null` (the checklist's `criteria` still worked fine, since its icon selector is far more specific). Fixed by searching directly for `[class*="bg_yellow"], [class*="bg_green"]` and taking the first candidate whose own class also parses to a width — no track-scoping step at all, since that combination is specific enough to the meter fill on its own.
- If this ever stops matching (0 criteria found, or `meter: null`), `readAnalysisAndClose()` dumps the first 10 matching elements' `class` values to stderr (`.icon--iconSize_sm` for criteria; `[class*="bg_yellow"], [class*="bg_green"], [class*="bg_gray.200"]` for the meter) — re-derive the logic from that the same way every other selector here was built, ideally with a real live round trip this time.

The frontend (`frontend/src/app/app.ts`) matches each plain-text checklist line back to its `criteria` entry by substring containment (see `findCriterionStatus()`) rather than trusting line order, since a criterion with an explanation reads as two separate lines in the plain-text `analysis` blob (title, then explanation) but one combined text block in `criteria`.

**Confirmed live (user-reported, jobIndex 35/44): the section-heading wording isn't fixed across verdicts, and an exact-match miss silently breaks both the meter and the list rendering at once, not just one of them.** A "C'est très bien" (strong-match) verdict rendered with no meter bar *and* every criterion as a plain paragraph instead of a colored list item — traced to `frontend/src/app/app.ts`'s `parseAnalysis()`: its `KNOWN_SECTION_HEADINGS` was an exact-match `Set` seeded only from "Un bon départ" samples ("Connaissances, qualifications et compétences **importantes**"), but this verdict's own heading is the bare "Connaissances, qualifications et compétences" — no "importantes" suffix. Since `isSectionHeading()` never matched, `parseAnalysis()` never entered a section (`inSection` stayed false, so every line fell through to a `paragraph` segment instead of `pushListItem()`), and the meter — only inserted at the moment a section heading is detected — never got inserted either. **Fixed**: matched by *prefix* now (`KNOWN_SECTION_HEADING_PREFIXES`, `normalized.startsWith(prefix)`) instead of an exact string, so both the "importantes" and bare wording match the same heading. If a *third* wording variant ever surfaces, the fix is the same shape: broaden the prefix/set, don't add a special case — and remember a miss here silently takes down the meter too, not just the list styling.

So job selection sorts the matched elements by their real on-screen position instead: `Promise.all(jobElements.map(el => el.boundingBox()))`, then sorts by `y` (then `x`) ascending, before indexing into that sorted array. The original mismatch was almost certainly comparing two different searches (jobup.ch's live listings and/or the CV-derived search term can vary between runs), not a bug — "the Nth job" is only a stable target within the same run/search, not across separate ones.

## Stopping an in-progress analysis

The frontend's "Stop analysis" button (see `frontend/CLAUDE.md`) calls `POST /api/cv-match/stop`, handled in `routes/api.js` alongside `POST /cv-match` itself:

- `routes/api.js` keeps a single module-level `runningCvMatch` slot (`{ processes: Set<ChildProcess>, stoppedByUser }` while a run is active, `null` otherwise) — the frontend UI only ever allows one analysis at a time (the CV Analysis button disables while `cvMatchPending()`), so one slot is enough. Since the search/per-job split (see the "jobup.ch CV-match automation" section above), one `/cv-match` request can have *several* child processes alive at once — the `jobup-search.js` run, and/or however many `jobup-cv-match.js` workers are in the current batch — so this became a `Set` rather than a single process: `spawnScript()` adds each child right after `execFile()` returns it and removes it again once that child's own callback fires, so the Set always reflects exactly what's currently running for this request.
- `POST /cv-match/stop` marks `current.stoppedByUser = true` and kills *every* process currently in `current.processes` (looping `killProcessTree()` over the Set) — which, on Windows, shells out to `taskkill /PID <pid> /T /F` per process: `/T` kills the whole process tree, `/F` forces it, which is the only reliable way to take down both a `node scripts/jobup-*.js` process and anything *it* spawned (the Playwright-launched Chromium browser), since Windows has no POSIX process-group signal for `child_process` to target directly. On non-Windows it falls back to `child.kill('SIGTERM')`. `runWorkersInBatches()` also checks `current.stoppedByUser` before starting each new batch, so a stop mid-range doesn't keep launching more workers than are already in flight — killing the *currently running* ones is what actually stops the analysis; the batch-loop check just stops new ones from starting.
- **Confirmed live (first real stop, via a user-supplied server log): an earlier version of `killProcessTree()` called `child.kill()` *before* `taskkill`** — originally to mark the Node `ChildProcess` itself as killed (`child.killed = true`, which makes `execFile`'s callback error carry `killed: true`) — and that raced against, and defeated, the taskkill cleanup. The log showed the sequence plainly: `stop requested by user; killing the running analysis process (pid 8364)` → `POST /api/cv-match/stop 200` → `analysis process was stopped by user request.` (the `/cv-match` callback correctly fired and detected the stop) → `taskkill for pid 8364 (stop cleanup): Command failed: taskkill /PID 8364 /T /F` / `Erreur : le processus "8364" est introuvable.` (French for "process not found"). `child.kill()` (called synchronously, first) terminates the node process almost immediately via Windows' `TerminateProcess` — so by the time the async `taskkill` call actually reached the OS, PID 8364 no longer existed for it to find, meaning `/T` never got the chance to walk its still-alive-at-that-point child tree. The analysis genuinely stopped (the top-level node process died and the callback fired correctly), but the Playwright-launched Chromium browser was almost certainly left running orphaned, since nothing else ever killed it. **Fixed**: `child.kill()` is no longer called before `taskkill` on Windows at all — its only real purpose (marking `err.killed` for detection) had already been made obsolete by `stoppedByUser` below, so there was nothing left to justify keeping it there once it was shown to actively undermine the tree-kill; `taskkill` alone now runs while the process (and its tree) is still alive. **Confirmed live (follow-up run, after restarting the server so the fix actually loaded — Node doesn't hot-reload `require()`'d route files, so the first retry attempt still hit the old, pre-fix code and reproduced the identical failure)**: a stop with the reordered code produced no `taskkill` error at all (silence — `killErr` was falsy), and a live process inspection (`Get-CimInstance Win32_Process`, filtered to the Playwright cache path) immediately afterward showed the stopped run's PID fully gone with no orphaned `chrome-headless-shell.exe`/`chrome.exe` left behind under it — only a *separate*, still-actively-running analysis's own (legitimate, non-orphaned) browser processes were present. The reordering fix is confirmed working end-to-end.
- **Aside, confirmed live while investigating the above**: even under the *old*, buggy ordering, no orphaned browser was ever actually found on inspection — Windows' own Job Object semantics (Node.js assigns non-detached spawned child processes to a job with kill-on-job-close, at least in recent Node versions) appear to cascade-kill a process's own children when it's terminated, independent of `taskkill`. That's a plausible extra safety net, not a reason to rely on it over the explicit, documented `taskkill /T /F` — but it explains why no leak was observed even before this fix landed.
- `current.stoppedByUser` (not the generic `err.killed`) is what determines whether a given process's failure gets reported as a stop rather than a generic failure — deliberately distinct from `err.killed`, because execFile's own 180s/300s `timeout` options (on `jobup-search.js`/each `jobup-cv-match.js` worker respectively) produce an identical-looking killed error for an unrelated reason (the run just took too long) and that case must keep reporting the existing generic failure behavior, not a misleading "stopped by user" message. This predates the search/per-job split and was **confirmed live** back when there was only one process to check it against — the callback logged `analysis process was stopped by user request.` on the actual user-triggered stop; unverified whether the exact same confirmation still holds now that it's checked per-process across a Set, though the logic itself (a plain boolean read, not anything process-count-dependent) doesn't obviously depend on that.
- Both `scripts/jobup-search.js` and `scripts/jobup-cv-match.js` register `SIGTERM`/`SIGINT` handlers (`activeBrowser`, set right after `chromium.launch()` and cleared in each script's own `finally { await browser.close(); }`) that close the browser gracefully before exiting, as a *best-effort* backstop — not the primary cleanup mechanism. Node's own docs note Windows' signal support for `SIGTERM` is unreliable (unlike POSIX), which is exactly why `taskkill /T /F` above is what's actually relied on to guarantee cleanup on this project's platform; the signal handlers are cheap insurance for whichever platform/signal combination does honor them, and are otherwise a no-op.
- The already-in-flight `POST /cv-match` request (the one the "CV Analysis" click made, and which the whole analysis runs inside — it's a single request that stays open awaiting the child process) still gets its callback invoked once the killed process actually exits, and still calls `res.json(...)` with the `'Analysis stopped by user.'` result — but the frontend (see `frontend/CLAUDE.md`'s `onStopClick()`) has already unsubscribed from that request's `Observable` by the time it calls `/cv-match/stop`, cancelling the underlying fetch client-side, so in practice this response is dropped and never reaches the UI; it exists mainly so the request completes cleanly server-side (`res.headersSent`/`res.writableEnded` are checked before calling `res.json()` there regardless, since a client-aborted connection is the expected common case here, not a bug to guard against with a crash).

## jobup.ch automated application drafting

`prepareJobApplicationDraft()` in `scripts/jobup-cv-match.js`, called from `runCvMatch()` right after a fresh or already-existing analysis is read: whenever a meter is present at all (`meter` non-null — green *or* yellow), it saves the job ("Sauvegarder") when `saveJob` is true and, when `easyApply` is true and "Candidature simplifiée"/"Continuer ma candidature" is available, opens it and prepares (never submits) a draft application there. Only the meter's *absence* (the "Vos talents correspondent mieux à d'autres opportunités" heading, confirmed live to render with no meter bar at all) skips this outright — this is entirely a side effect of a CV-match run with a meter, not a separately triggered action. `ignoreYellowMeter`, when true, additionally excludes a yellow meter specifically (so only green then qualifies); when false (the default), green and yellow are treated identically. `saveJob` and `easyApply` gate their two actions independently of each other and of `ignoreYellowMeter` — a user can enable either, both, or neither. All three booleans come from the frontend's "Job filters" dropdown (see `frontend/CLAUDE.md`) and are passed straight through `POST /api/cv-match` → the script's CLI args; the script itself ignores them entirely (never even reads them) whenever `meter` is null.

**Unlike everything documented above, none of this has been verified against the live site** (no jobup.ch session was available in this environment) — built from the user's own step-by-step description and a few pasted DOM snippets. Expect this to need the same kind of live iteration every other selector in this file originally did; when it breaks, dump the DOM/`ariaSnapshot()` and fix from that rather than guessing again.

- **New tab, same script**: "Candidature simplifiée"/"Continuer ma candidature" opens the application in a new tab. This doesn't need a second script or browser — `page.context().waitForEvent('page')`, raced against the click that opens it, hands back that new tab as an ordinary Playwright `Page` in the same process/session, driven with the same `page.locator(...)` API from then on (see `prepareJobApplicationDraft()`).
- **The job page's "Sauvegarder" button's accessible name is not "Sauvegarder"** — confirmed live from a user-supplied DOM snippet: `<button id="vacancy-bookmark-cta-info" aria-label="Sauvegarder l'emploi" aria-pressed="false" data-cy="bookmark-button-unchecked">…Sauvegarder</button>`. An `aria-label` always overrides an element's own text for accessible-name purposes, so its real accessible name is "Sauvegarder l'emploi" — the original `getByRole('button', { name: /^sauvegarder$/i })` (anchored to an *exact* match) matched nothing and silently logged "button not found/visible" instead of clicking it. Fixed by targeting the confirmed `id`/`data-cy` first, with an *unanchored* `/sauvegarder/i` role match as a last resort (anchored exact-match regexes are risky on this site whenever a button might carry a descriptive `aria-label` beyond its visible text). It's also a toggle (`aria-pressed`/`data-cy="bookmark-button-unchecked"` vs. presumably `"…-checked"` when already saved) — guarded via `aria-pressed` so a job saved by a previous run doesn't get un-saved by clicking it again. The *other* "Sauvegarder" button (on the application page itself, in `fillApplicationDraft()`) was proactively unanchored the same way on the assumption it's equally likely to carry an enriched `aria-label`, though that specific one hasn't been confirmed live either way. The "Ajouter" confirm-attach button was deliberately **not** unanchored the same way — "Ajouter d'autres documents" (a different, already-clicked button) is plausibly still visible in the same panel, and an unanchored `/ajouter/i` risks `.first()` grabbing that one instead; it now dumps all visible buttons' text/`aria-label` to stderr if the exact match ever misses, rather than guessing further.
- **That same "Sauvegarder" button's `id` is duplicated on the page** — confirmed live (second round): `page.locator('#vacancy-bookmark-cta-info')` matched *two* elements sharing that id, jobup.ch's usual habit of duplicating markup for responsive mobile/desktop layouts (already known from job cards/the filter bar elsewhere in this file) but this time via a literally duplicated `id` rather than a duplicated class. One instance resolves to a 0×0 box — its own computed style still says `display:flex`/`visibility:visible` (an *ancestor*, not the element itself, is what's actually hidden) — so `.first()` on the unfiltered locator silently grabbed that one, `isVisible()` correctly reported `false`, and the button was never clicked even though a real, visible copy existed. Fixed by scoping every candidate to `:visible` (`'#vacancy-bookmark-cta-info:visible'`, `.and(page.locator(':visible'))` for role/text-based locators — `Locator.and()` needs Playwright ≥1.34; this project runs 1.63). Since this pattern is now confirmed to extend beyond job cards to arbitrary buttons/ids, every `.first()`-consuming locator added for the application-drafting flow (`generateCoverLetterIfNeeded()`, `attachMissingDocuments()`, `answerYesNoQuestions()`, the application-page "Sauvegarder", "Candidature simplifiée"/"Continuer ma candidature") was proactively scoped to `:visible` the same way, even where not individually confirmed live — cheap insurance against the same failure mode recurring silently. `browser.newPage()` also now sets an explicit `{ width: 1440, height: 900 }` viewport rather than relying on Playwright's headless default (1280×720) — a different default viewport could itself land on a different responsive breakpoint than whatever a normal full-size browser window (used to inspect these pages live) shows, independent of the duplicated-markup issue above.
- **Not every job has a "Candidature simplifiée"/"Continuer ma candidature" button at all** — confirmed live: a job posted through an external/agency application flow (seen on a listing from staffing agency Academic Work Switzerland SA) has no on-site simplified-application button whatsoever; its only apply control is `[data-cy="apply-button-external"]` ("Postuler"), which redirects off jobup.ch entirely to the poster's own system. `prepareJobApplicationDraft()` checks for that `data-cy` when the simplified-application button isn't found, so this expected, unsupported case is logged distinctly ("this job only offers an external application...") rather than looking identical to a genuinely broken/renamed selector.
- **A logged "clicked" doesn't mean the save actually persisted** — confirmed live: the log showed `clicked "Sauvegarder" (save job) on the job page.` for a run, but the button still showed unsaved ("Sauvegarder", not "Sauvegardé") when the same job page was checked afterward in a real, logged-in browser. The click event fires and the accessible-name/`aria-pressed` toggle can update client-side, but the actual bookmark-save request is asynchronous — and `prepareJobApplicationDraft()` was returning (and `runCvMatch()`'s `finally { browser.close() }` firing) within moments of the click, likely cancelling that request before jobup.ch's server ever processed it. Fixed with `waitForAttributeValue()`: after clicking, polls the button's `aria-pressed` attribute (250ms interval, 5s timeout) until it actually reads `"true"` (logged either way — "confirmed" vs. "never became true within 5s"), then adds a further 1.5s buffer before moving on. The same fix (a flat 1.5s buffer, no attribute to poll for a one-shot save-draft action) was applied after the application-page's own "Sauvegarder" click in `fillApplicationDraft()`, since it has the identical shape — click, then straight into `applicationPage.close()`. Neither of these has been re-confirmed live yet as actually fixing the underlying persistence (only that `aria-pressed` now flips and is given time to settle) — if a save still doesn't stick after this, the network request itself (not just the timing) needs inspecting live.
- **The async-request-cancellation theory above turned out to be wrong** — confirmed live on the very next run: the log showed `clicked "Sauvegarder" but aria-pressed never became "true" within 5s`, i.e. `aria-pressed` never flipped even *client-side*, ruling out "the request was cancelled before completing" (that would still require the client-side toggle to have happened first). Since Playwright's own `.click()` actionability checks (visible/stable/enabled/receives-pointer-events at that exact point) passed without throwing — meaning the click really did land on this specific, on-screen, interactive element — the remaining plausible explanation is that this SPA hadn't finished *hydrating* a working click handler onto the button yet when the click fired; Playwright's checks verify the DOM's static state, not whether React/whatever framework has wired up its listeners. Mitigated with a 1.5s settle wait before the click (giving hydration more time) plus richer diagnostics if `aria-pressed` still doesn't flip: the button's `outerHTML` right after the click, every `console` message logged during the click window, and any request/response whose URL matches `/bookmark|favori|save/i`. **Still unconfirmed** whether the settle wait actually fixes it or the diagnostics are what's needed next — the next run's logs will show which.
- **Resolved (the diagnostics were what was needed): the hydration theory was also wrong, and the save was actually succeeding all along.** The captured network activity from the next run showed `request POST https://www.jobup.ch/api/v1/user/bookmark/job` → `response 200` — a genuine, successful save. The captured `outerHTML`, though, revealed the real cause: jobup.ch has a *second*, unrelated bookmark control for the same job — a compact icon-only button (`id="vacancy-bookmark-icon-<jobId>"`, `data-cy="bookmark-icon-unchecked"`, no visible text) that carries the exact same `aria-label="Sauvegarder l'emploi"` as the intended `#vacancy-bookmark-cta-info` CTA. The previous locator combined all three candidates with `.or()` — a *union*, not a priority order — so `.first()` picked whichever of the two "sauvegarder"-labeled elements happened to come first in DOM order, non-deterministically landing on the icon variant. Clicking it does genuinely fire the real save (confirmed by the 200), but its own `aria-pressed` isn't kept in sync reactively — which is exactly why polling that attribute kept reporting failure on an actual success. Fixed two ways: (1) the three candidates (`#vacancy-bookmark-cta-info:visible`, the `data-cy` variants, the unanchored role match) are now tried in **strict priority order** — a `for` loop that stops at the first one found visible — rather than unioned, so the confirmed-correct CTA is used whenever present at all; (2) success is now confirmed via `page.waitForResponse()` matching `POST .../api/v1/user/bookmark/job`'s actual status, the real server-side ground truth, instead of trusting any particular element's DOM attribute. `waitForAttributeValue()` (the aria-pressed-polling helper) was removed as dead code once nothing called it anymore. The application-page's own final "Sauvegarder" (in `fillApplicationDraft()`) doesn't have a known endpoint to confirm against yet, so — rather than guess one — it now captures and logs every POST/PUT response seen during/after that click, the same evidence-gathering approach that found the bookmark endpoint, so the real one can be targeted precisely once a live run shows it.
- **`generateCoverLetterIfNeeded()`'s required-field detection over-matched** — confirmed live: a job whose cover-letter field visibly had *no* asterisk still got a cover letter generated. The walk-up-from-the-label loop searched *all descendants* of an ever-growing ancestor container at each hop, up to 6 hops — by hop 5–6 the container had grown large enough to also contain some *other*, unrelated field's own required-marker elsewhere on the form, which was then mistaken for this field's own marker. Cut down to 2 hops: a real miss (a genuinely required field whose marker sits further away structurally than that) is the safer failure mode here than generating an unwanted cover letter, and a diagnostic log (`cover-letter field detected as required; marker found: <outerHTML>`) now shows exactly which marker triggered a positive so this can be recalibrated from real evidence if 2 hops turns out to be wrong in the other direction.
- **`attachMissingDocuments()`'s "already attached" check false-positived on two files that visibly weren't attached** — confirmed live via a user-supplied screenshot: only one of the three files was actually shown as an attached-document card, but the other two were both logged as "already attached; skipping." Suspected cause: the check is a page-wide exact-text search (`getByText(fileName, { exact: true })`), which can't distinguish an actual attached-document card from that same filename appearing as a *selectable option* inside a still-open "Sélectionner depuis le profil" picker — and the previous file's picker wasn't explicitly confirmed closed before moving on to the next file's check, which is exactly the pattern seen here (files 2 and 3 false-positived right after file 1's own successful attach). Fixed two ways: (1) after a successful "Ajouter" click, explicitly waits (5s) for the "Sélectionner depuis le profil" picker to become hidden before continuing to the next file, logging if it doesn't; (2) the "already attached" branch now dumps the matched element's nearest classed-ancestor `outerHTML` to stderr, so if a false positive still happens, the log shows directly whether it's a real attached-card or a picker leftover instead of requiring another guess-and-check round trip.
- **The above fix wasn't enough — the false positive recurred on the 3rd file, and the dumped diagnostics from the fix above pinned down the real cause**: confirmed live via a user-supplied screenshot showing only 2 of 3 documents actually attached, plus the matched-element dumps from both a genuine and a false-positive case in the same run. The genuine already-attached match (file 1, from an earlier run) was a real `<a href="https://media.jobs.ch/media/...">` download link; the false positive (file 3) matched a plain, href-less `<span class="c_link.defaultDark.base groupHover:c_link.defaultDark.hover">` — link-*styled* but not a real link, i.e. a still-open picker's selectable file option, not an attached-document card. This also explained why the previous fix's `waitFor({ state: 'hidden' })` silently succeeded (no error logged) even though the picker's actual file-list panel was still open: `selectFromProfile` was bound to the *menu-item label* that was clicked to open the picker (a one-off entry in the "Ajouter d'autres documents" dropdown), not the file-list panel itself — that label closing (which it does immediately, as any clicked menu entry does) was never a reliable signal that the panel behind it had closed too. Fixed two ways: (1) a new `isRealAttachedDocumentLink()` helper walks up to 4 hops from a text match looking for an `<a>` ancestor with a real `href`, and the "already attached" check now requires that in addition to the text match — a text-only match (tag dumped to stderr) is logged and treated as *not* attached, proceeding to attach it for real, rather than skipped; (2) since the picker's real close state has no known reliable selector to wait on, an unconditional `page.keyboard.press('Escape')` now follows every successful "Ajouter" click, a generic, structure-independent way to force-close any lingering picker/modal regardless of what it's actually built from. The original `waitFor({ state: 'hidden' })` wait on `selectFromProfile` was kept as an informational step (its log message reworded to say what it actually confirms — the label, not the panel), since removing it outright would lose that signal for free.
- **Cover letter** (`generateCoverLetterIfNeeded()`): only generates if the field is both required and empty. "Required" is detected by a `<span class="c_colorPalette.errorMain color-palette_input.default">*</span>` (matched via `[class~="c_colorPalette.errorMain"]`, since — like the CV-match meter/status classes — that's one literal class token containing a dot, not two classes) found within a few DOM hops of the "Écrivez votre lettre de motivation ici" label; "empty" is checked via the nearby `textarea`/`[contenteditable]`'s value. If required and empty, clicks "Générer" and returns without waiting; `fillApplicationDraft()` then attaches documents and answers questions while it generates, and calls `waitForCoverLetterText()` right before the final "Sauvegarder". That polls the field (500ms) until it holds non-empty text unchanged for 3s (generation may stream in), up to 90s, then saves either way, logging which. **Confirmed live on jobs.ch** that the old flat 5s wait saved an empty cover letter. Because the 2-hop label walk can stop at the required marker before reaching the field, the field alone is searched for up to 5 hops (read-only, so widening it can't cause the over-matching the marker search had); if no field is found it falls back to a flat 15s wait. Each `jobup-cv-match.js` worker's execFile timeout was raised 180s → 300s in `routes/api.js` to leave room for this on top of a slow analysis. **If the field is not required but already has leftover content** (e.g. from an earlier run before the over-matching bug above was fixed, or a value the site itself pre-filled), it's cleared via the new `clearCoverLetterField()` helper instead of being left in place — `.fill('')` for a `<textarea>`, or a direct `textContent = ''` plus a dispatched `input` event for `[contenteditable]` (`.fill()` doesn't work on contenteditable elements, and the page needs an `input` event, not just the DOM mutation, to notice the field emptied — same reasoning as other event-driven state in this flow). The hop loop now also hoists a `fieldLocator` reference to the found textarea/contenteditable (previously scoped inside the loop and discarded) so this clearing step has something to act on. Unverified live — no confirmed run has hit the not-required-but-has-content case yet.
- **Documents** (`attachMissingDocuments()`): for each of `REQUIRED_DOCUMENT_NAMES` (`Certificat de travail L HERAULT 2026.04.pdf`, `Diplôme Bachelor 2020.pdf`, `LR-ITADV.pdf`), skips it if that exact filename is already visible as a link on the page, otherwise clicks "Ajouter d'autres documents" → "Sélectionner depuis le profil" (a `<span class="tw_wrap w_[max-content]">`, matched here by text alone rather than that class, to avoid CSS-escaping the literal `[`/`]` in `w_[max-content]`) → the matching filename → "Ajouter" — repeating that whole sequence independently per file, per the user's spec, rather than trying to batch-select all three at once.
- **Yes/no questions** (`answerYesNoQuestions()`): clicks every `<span class="ta_center white-space_pre-line w_100%">Oui</span>`-style "Oui" option found (matched by exact text "Oui"), unconditionally — **note**: this answers "Oui" regardless of what the question actually asks, which was explicitly requested but is worth re-confirming case by case, since it could misrepresent the user on questions where "Non" would be the honest/appropriate answer (e.g. work permit, relocation, availability). **Speculative, unverified addition**: before clicking each "Oui", a new `isOptionSelected()` helper checks `aria-pressed`/`aria-checked`/`aria-selected` on the option itself and up to 2 ancestors (mirroring the aria-pressed pattern already confirmed for the job-page bookmark button) — if "Oui" already reads as selected, the click is skipped (avoiding a risk of toggling it back off); otherwise, the function walks up to 2 ancestor hops looking for a same-question "Non" counterpart (`getByText('Non', { exact: true })`) and, if found and it reads as currently selected, clicks it first to deselect before selecting "Oui". This whole "Non" half is unconfirmed against the live site — there's no DOM evidence yet for how (or whether) jobup.ch marks a Yes/No option as selected, or for a "Non" element's actual structure/proximity to its "Oui" sibling — so it's scoped tightly (2 hops, `:visible`-only, 1s timeout) and wrapped so a failure to find/click "Non" never blocks selecting "Oui". Treat any live failure here the same as everything else in this section: dump the DOM rather than guess a fix.
- **Final step**: `fillApplicationDraft()` always ends by clicking "Sauvegarder" on the application page itself — **never** the actual submit button — so the application is saved as a draft, not sent.
- Every step in this whole flow is wrapped so a failure just logs and moves on (or is caught at the top by `prepareJobApplicationDraft()`'s own try/catch) rather than throwing — a problem here must never invalidate the CV-match analysis result that already succeeded before this ran.

## Backend build/deployment

`npm run build` (→ `node build.js`, see its own header comment for the full picture) bundles and minifies the root Express app with `esbuild` into a self-contained `dist/` folder:

- `dist/bin/www.js` — the server entry point, with `app.js` and every `routes/*.js` file it requires collapsed into this one bundled/minified file.
- `dist/scripts/jobup-login.js` / `dist/scripts/jobup-search.js` / `dist/scripts/jobup-cv-match.js` — each bundled as its own **separate** entry point, deliberately not merged into the server bundle: `routes/api.js` spawns each as an independent `node <scriptPath>` child process (see its own comments), not a function call, so they have to keep existing as real, standalone, directly-executable files at that same `scripts/<name>.js` path. `scripts/jobup-shared.js` isn't its own entry point — nothing spawns it as a process, so esbuild just inlines its code into whichever of the two files above `require()` it, same as `jobup-login.js`'s code already gets inlined into both.
- `dist/views/`, `dist/public/` — copied as-is (Jade templates and static assets are read/served at runtime, not bundled).
- `dist/package.json` (pruned to just the production `dependencies`, `start` pointing at `bin/www.js`) and `dist/package-lock.json` — for `npm ci --omit=dev` on the deploy target. `dist/.env.example` is copied for reference; `dist/.env` is never created by the build — add the real one directly on the target after deploying.
- Real npm dependencies (`express`, `playwright`, `dotenv`, ...) are deliberately left external (`packages: 'external'`), not inlined — `playwright` ships native browser binaries a bundler can't meaningfully embed, and a real `npm install`/`npm ci` on the target was already the expected deployment step (see the "jobup.ch login automation" section's `playwright`-as-a-direct-dependency note). So this bundles/minifies just this app's own first-party code; `node_modules` still needs installing separately on the server. **Deploy**: copy `dist/` to the target, `npm ci --omit=dev` inside it, add a real `.env`, then `npm start`.

**`APP_ROOT`/`process.cwd()`, not `__dirname`, for repo-root-relative paths — this is load-bearing for the build above, not just a style choice.** `app.js` (views/public paths), `routes/api.js` (`.env` path, and each of the three scripts' own paths — `jobup-login.js`, `jobup-search.js`, `jobup-cv-match.js`), and `scripts/jobup-login.js` (its own `.env` rewrite path) all resolve these via `process.cwd()` (aliased `APP_ROOT` in the first two). Confirmed live: an earlier version used `path.join(__dirname, ...)` for all of these, which broke once bundled — `__dirname` for code merged into a single bundled file resolves to wherever *that output file* physically sits, not the original source file's own directory, and different source files here originally assumed different nesting depths (`app.js` at the repo root; `routes/api.js` one level down, using `path.join(__dirname, '..', ...)` to get back to the root). Merging them into one bundle can't simultaneously satisfy both assumptions — whichever depth the output file ends up at, at least one of them resolves wrong (e.g. a root-level bundle makes `routes/api.js`'s `'..'` overshoot *outside* the deployed `dist/` folder entirely, looking for `scripts/`/`.env` next to `dist/` rather than inside it). `process.cwd()` has no such dependency on bundle nesting — it works identically for the unbundled source (`npm start`, always run from the repo root) and the bundled `dist/` output (started from its own root the same way, e.g. `cd dist && npm start`), regardless of how deep any individual bundled entry file ends up. **If a future change adds a new repo-root-relative path in any of these three files (or a new file that gets bundled the same way), use `process.cwd()`/`APP_ROOT`, not `__dirname` — a straight port of one of those files' existing `__dirname`-based patterns will silently break the same way once bundled.**

## Architecture notes

- **Root Express app**: classic MVC-ish layout — `app.js` wires middleware and mounts routers from `routes/`, `bin/www` creates the HTTP server and normalizes the port, views render with Jade from `views/`. Static assets are served from `public/`.
- **Playwright**: configured at the root (`playwright.config.ts`) with `testDir: './tests'`, running against chromium/firefox/webkit. No `baseURL`/`webServer` is configured, so specs must `page.goto()` a full URL. A GitHub Actions workflow (`.github/workflows/playwright.yml`) runs `npx playwright test` on push/PR to `main`/`master`.
  - `tests/example.spec.ts` is still the default template pointed at `playwright.dev`.
  - `tests/jobup-login.spec.ts` automates navigating to jobup.ch's login page only (no credentials): dismisses whichever cookie-consent variant appears, clicks "Se connecter", and asserts the login heading/email textbox appear (see the "jobup.ch login automation" section above for both cookie-consent variants and how they were found).
